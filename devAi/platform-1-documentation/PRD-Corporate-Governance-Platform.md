# وثيقة المتطلبات والمواصفات الشاملة
## منصة التوثيق التقني المؤسسي وإدارة التغييرات والحوكمة

**اسم المشروع:** Corporate Technical Documentation & Change Governance Platform
**نوع المشروع:** منصة ويب مؤسسية ديناميكية قابلة للتخصيص والتوسع
**الجهة المستفيدة:** شركة برمجيات مالية تعمل على أنظمة الدفع والتكاملات التقنية
**تاريخ الإصدار:** 2026-10-11
**حالة الوثيقة:** مسودة أولى للمراجعة والاعتماد

---

## 1. الملخص التنفيذي

تهدف المنصة إلى إنشاء مرجع مركزي وموحد لجميع المعلومات التقنية التي تخص الشركة، بما في ذلك واجهات API، والسيرفرات، والأنظمة، والتكاملات، والجهات المرتبطة، والإعدادات، والوثائق الفنية، وأي نوع آخر من الأصول التي تحتاج الشركة إلى توثيقها.

**المبدأ الأساسي:** المنصة مستقلة عن الأنظمة التشغيلية الفعلية. فهي ليست نظاماً لتنفيذ التغييرات على API أو السيرفرات، ولا تتحكم مباشرة في تشغيل أنظمة الدفع. وإنما توفر سجلاً مؤسسياً موثقاً لما تم تسجيله من معلومات وتغييرات وطلبات وموافقات وأدلة.

> كل أصل له سجل، وكل سجل له تاريخ، وكل تغيير مسجل له سبب ومسؤول وأدلة، وكل موافقة لها هوية وقرار، وكل قالب أو سياسة لها إصدار، وكل عملية تخضع لصلاحيات واضحة.

## 3. المبادئ الأساسية للمنصة

1. **الاستقلال:** المنصة لا تنفذ التغييرات، ولا تمنعها. وظيفتها التوثيق والموافقة والسجل.
2. **الفصل بين الواقع والتوثيق:** تميّز بين الحالة المسجلة، المعتمدة، والفعلية.
3. **الديناميكية الكاملة:** كل شيء قابل للتكوين من خلال المنصة دون تعديل الكود.
4. **المحافظة على التاريخ:** لا يمحو أي تعديل السجل السابق.
5. **فصل الصلاحيات:** منع مقدم الطلب من اعتماد طلبه.

## 5. توثيق API

### التصنيف حسب الاتجاه

- **Provided APIs:** واجهات تقدمها الشركة للبنوك والتجار والأنظمة الخارجية
- **Consumed APIs:** واجهات تستخدمها الشركة من البنوك، AML/KYC، المحاسبة

### حقول توثيق API (قابلة للتخصيص)

| الحقل | النوع | الإلزامية |
|-------|-------|----------|
| اسم الواجهة ومعرّفها | نص | إلزامي |
| وصفها والغرض | نص طويل | إلزامي |
| الجهة المالكة/المقدمة | مرجع | إلزامي |
| الجهة المستهلكة | مرجع | إلزامي |
| النظام المرتبط | مرجع | إلزامي |
| الإصدار | نص | إلزامي |
| البروتوكول وطريقة الاتصال | قائمة | إلزامي |
| العمليات/المسارات | جدول متكرر | اختياري |
| بيانات الطلب والاستجابة | JSON/نص | اختياري |
| رموز الأخطاء | جدول | اختياري |
| آلية المصادقة | قائمة+نص | إلزامي |
| البيئات المستخدمة | اختيار متعدد | إلزامي |
| حالة التوثيق | قائمة | إلزامي |

## 6. دورة التغيير الرسمية

```
المرحلة 1: إرسال الطلب
الجهة الطالبة → بريد Outlook → الموظف المسؤول

المرحلة 2: تسجيل الطلب في المنصة
المسؤول يرفق البريد الأصلي → ينشئ طلب تغيير → يحدد الأصل المعني

المرحلة 3: المراجعة
التحقق من الاكتمال → تحديد الجهات المتأثرة

المرحلة 4: الموافقات (مسار ديناميكي)
المشرف المباشر → مدير الإدارة → المدير العام (حسب الخطورة)

المرحلة 5: التوثيق
تسجيل التوثيق الجديد + ربطه بالطلب + ربطه بالإصدار السابق

المرحلة 6: الإغلاق
حفظ: النتيجة + الموافقات + الأدلة + التواريخ
```

## 8. محرك الموافقات الديناميكي

يستطيع المسؤول تحديد:
- ترتيب خطوات الموافقة والدور المطلوب في كل خطوة
- هل الخطوة إلزامية أم مشروطة
- قواعد التصعيد عند الغياب
- اشتراط الاعتماد الإضافي حسب مستوى الخطورة
- منع مقدم الطلب من اعتماد طلبه (فصل المهام)

**ما يُحفظ تاريخياً:** نسخة من مسار الموافقة المطبَّق وقت الطلب (لا تؤثر التعديلات المستقبلية على السجل التاريخي).

## 10. نظام الصلاحيات

### الفصل الثلاثي

| العنصر | وظيفته |
|--------|--------|
| المستخدم | الموظف الحقيقي بحساب وهوية |
| الدور | مجموعة صلاحيات قابلة للإسناد |
| نطاق الصلاحية | الأصول والأقسام والبيانات المسموحة |

### مستويات الصلاحيات

```
على مستوى الوحدة    → هل يدخل قسم API؟
على مستوى التصنيف  → هل يرى توثيق البنوك أم فقط التجار؟
على مستوى السجل    → هل يطلع على تكامل بنك محدد؟
على مستوى العملية  → هل يضيف؟ يعدّل؟ يعتمد؟
على مستوى الحقل    → هل يرى أو يعدّل بيانات المصادقة؟
```

**قاعدة ذهبية:** تطبيق الصلاحيات في الخادم وليس فقط في واجهة المستخدم.

## 11. التصدير الديناميكي

### التسلسل الهرمي للقوالب

```
قالب الشركة (سياسات إلزامية + هوية مؤسسية)
    ↓
قالب الإدارة (احتياجات الإدارة المعتمدة)
    ↓
قالب نوع التوثيق (API / سيرفرات / تقارير تدقيق)
    ↓
إعدادات المستخدم (تفضيلات شخصية محدودة)
```

### أنواع التصدير

| النوع | التعريف |
|-------|---------|
| تصدير شخصي | استخدام يومي وفق خيارات المستخدم |
| تصدير مشترك | مبني على قالب معتمد للفريق/الإدارة |
| تصدير رسمي معتمد | يخضع لقواعد محددة وقد يتطلب رقم إصدار وبصمة تحقق |

### صيغ التصدير المستهدفة
PDF | Word | Excel | CSV | HTML | JSON | OpenAPI

## 16. النتيجة النهائية المستهدفة

تستطيع الإدارة في أي وقت الإجابة عن:
- ما الأنظمة وواجهات API والسيرفرات التي تمتلكها الشركة؟
- من المسؤول عن توثيق كل أصل؟ وما الإصدار المعتمد حالياً؟
- ما التغييرات التي طُلبت أو اعتُمدت أو رُفضت؟
- من وافق على كل تغيير، ومتى، وبأي صلاحية؟
- ما الجهات المرتبطة بإصدار معين؟
- ما التغييرات التي اكتُشفت دون طلب رسمي؟
- هل يمكن إضافة نوع توثيق أو قالب أو دور جديد دون إعادة بناء النظام؟
